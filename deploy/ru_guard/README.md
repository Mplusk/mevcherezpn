# Защита серверной маршрутизации

Эти инструменты готовят два override шаблона серверной маршрутизации Hiddify
Manager 14.2.0. Они не устанавливают базы и не применяют настройки панели.
Не запускайте установщик на действующей панели до завершения всех проверок ниже.

## Обязательные предварительные условия

1. На **каждом** узле, включая основной, должны быть доступны два проверенных
   файла runetfreedom в root-owned каталоге VPS `/root/services/gamelife-vpn/ru-assets`,
   read-only bind которого должен быть доступен по пути
   `/opt/hiddify-manager/services/xray/bin/gamelife` внутри контейнера.
   Ссылка `current` внутри bind должна указывать на проверенную ревизию,
   доступную на чтение обоим ядрам. Mount должен сохраняться при пересоздании.
2. Проверить реальным Xray на каждом узле, что оба файла загружаются через
   `ext:gamelife/current/geosite.dat:ru-blocked` и
   `ext:gamelife/current/geoip.dat:ru-blocked`. Обеспечить последнюю рабочую версию,
   атомарное обновление и безопасный controlled reload. Без этих файлов
   сгенерированный Xray с соответствующими правилами может не запуститься.
3. Два проверенных SRS должны находиться в `current/geosite-ru-blocked.srs` и
   `current/geoip-ru-blocked.srs` того же bind; шаблон применяет их локально.
   Проверить корректность файлов и доступность для hiddify-core на каждом узле.
4. До активации включить блокировку BitTorrent в настройках панели и проверить,
   что конечные активные правила и порядок не дают исключению обойти private или
   BitTorrent. Hiddify-core должен поддерживать действие `resolve` и иметь
   работающий DNS по умолчанию. Новый early resolve меняет способ разрешения
   имён и должен быть проверен на реальном трафике, включая мосты.
5. Проверить готовность на всех дочерних узлах, включая реальные конфигурации
   обоих ядер. Исключения нельзя активировать, пока хотя бы один узел не готов.

## Запись шаблонов

Из каталога `deploy/ru_guard` на основном VPS, с правами root:

```sh
python3 template_install.py /root/services/gamelife-vpn/admin-access.json /root/services/gamelife-vpn/guard-backups/route-before.json
```

Установщик ищет built-in шаблоны по slug и проверяет их структуру. При чужом
override или неизвестном формате он прекращает работу до изменений. Резервная
копия создаётся эксклюзивно с правами 0600 **до** изменений. Если PATCH
завершился ошибкой или ответ не дошёл, производится попытка восстановления,
включая последний затронутый шаблон. Если восстановить не удалось, в логах
выводится только тип ошибки; восстановить содержимое необходимо из backup
через API до применения конфигураций. Access state и backup не публиковать.

После установки overrides проверить их распространение и только затем
применить конфигурации панели. Контролировать здоровье Xray и hiddify-core на
каждом узле и реальное соединение клиентов. Если проверка не прошла, вернуть
обе записи через API из backup и повторно применить предыдущую конфигурацию.

## Правило исключения

После предварительных проверок можно добавить исключение через API:

```sh
python3 outbound_install.py install /root/services/gamelife-vpn/admin-access.json /root/services/gamelife-vpn/guard-backups/outbounds-before.json
```

Утилита проверяет включённый Block с ожидаемыми RU-правилами и Direct по
умолчанию, до записи сохраняет исходный список с правами 0600, создаёт отдельный
direct outbound и ставит его непосредственно перед Block. Порядок всех прочих
правил и значение default сохраняются. При неожиданной существующей записи
или конкурентном изменении операция прекращается для ручной проверки. Если
ответ потерялся после commit, откат перепроверяет состояние и отключает
созданную запись, сохраняя её ID. Она останется видимой в панели, но не должна
применяться как правило. Не изменять outbounds параллельно с установкой.

Для обратимого снятия исключения используйте `outbound_install.py remove` с
новой уникальной резервной копией. Это отключает запись через PATCH вместо
DELETE, сохраняя ID и пользовательские привязки. Повторный `install` включает
её снова. Изменение outbounds может немедленно запустить синхронизацию и
применение на дочерних узлах. Поэтому перед записью нужно подтвердить, что
все узлы готовы; после — проверить распространение и здоровье. Утилита не
запускает отдельный Apply Configs и сама не проверяет здоровье узлов.

## Прототип транзакции

`transaction.py` — **только прототип**, без производственного адаптера и
команды запуска. Он демонстрирует последовательность: проверка четырёх узлов,
установка и проверка mount/баз, backup и установка шаблонов, установка правила,
Apply, проверка каждого data plane и подписки. В случае ошибки сначала
отключается созданное правило, затем восстанавливаются шаблоны, применяется и
проверяется прежняя конфигурация; только после этого вызывается откат mount.
При непроверенном откате нужно сохранить доступные данные и изучить состояние
узлов и резервные копии вручную. Если mount rollback сам завершился ошибкой,
какие mount действительно остались, определяет журнал адаптера; прототип не
гарантирует их наличие.

Для production нужен отдельно проверенный адаптер, который устанавливает
подлинность серверов, фиксирует собственные изменения mount до каждого шага,
атомарно разворачивает базы и переживает обрыв связи/перезапуск оператора.
Он обязан проверять содержимое и устойчивость mount на каждом узле, версии и
валидность обоих ядер, распространение панели и реальный безопасный e2e-трафик,
а также доступность подписки. Булевы значения callback не являются заменой
таких проверок. Это пока не реализовано и тесты mock не подтверждают deploy.

## Проверки

```sh
python3 -m unittest discover -s deploy/ru_guard -p 'test_*.py' -v
```

Unit-тесты не заменяют интеграционных проверок с реальными Xray и hiddify-core.
Репозиторий runetfreedom и его лицензия указаны в `deploy/geo/README.md`.
