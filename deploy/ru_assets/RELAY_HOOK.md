# Прототип relay CI hook

`relay_hook.py` — изолированная модель решения; она **не подключена** к
`deploy/relay/dispatcher.py`, не имеет production adapter и не запускает
операции на VPS сама. Mock-тесты не доказывают работу настоящего деплоя.

* Имеющийся корректный read-only mount только проверяется: install, recreate,
  rollback и detach не вызываются. Если mount отличается или проверить его не
  удалось, операция завершается ошибкой и не пытается его снять.
* Без mount обычный CI не пересоздаёт панель. Явный staging разрешается только
  после preflight для точного SHA: current main и CI, SSH host identity,
  образ/Compose, assets, сети, текущая панель, независимый VPN, отсутствие
  зависимости шаблонов от mount, готовность rollback и durable journal.
* Если установка завершилась ошибкой, состояние перечитывается. При наличии
  mount откат разрешён только если доказано отсутствие зависимости шаблонов.
  Если состояние неизвестно, rollback или проверка прежнего VPN не прошли,
  выдаётся `RollbackUnsafe`: никакой автоматической повторной попытки снять
  mount. Сам production adapter должен вести журнал intent до каждого действия.

## Двухфазное обновление dispatcher

Работающий Python dispatcher уже загрузил свой собственный `FILES` allowlist.
Записать новый `dispatcher.py` во время release недостаточно: текущий процесс
не превращается в новую версию и не сможет безопасно загрузить новый hook.
Поэтому production integration потребует минимум два отдельных вызова:

1. CI проверяет и устанавливает dispatcher поколения 1. В текущем процессе
   staging hook **не вызывается**. Старый allowlist продолжает определять,
   какие файлы этот процесс вообще способен доставить.
2. Новый SSH-вызов запускает уже новое поколение dispatcher. Оно повторно
   проверяет, что SHA всё ещё указывает на current `main` и Verify успешно
   завершён для него, доставляет hook по новому allowlist и только при явно
   разрешённом staging запускает безопасный preflight. При обновлении SHA
   между шагами нужна новая полная проверка.

`dispatcher_generation` в модели должен фиксироваться текущим процессом при
запуске. Повторно прочитать уже заменённый файл dispatcher с диска и объявить,
что новый код загружен, недостаточно. Shared deployment lock должен покрывать
весь preflight, staging, проверку и rollback. Интеграция не должна публиковать
вывод `docker compose config`, env, приватные адреса подписок или credentials.

Даже готовый hook не защищает от другого пути, который пересоздаёт панель без
asset override. Перед production нужно закрыть все такие пути, проверить
сетевые алиасы и тома, и подтвердить независимый реальный VPN после recreate и
rollback. При прерывании с неизвестной фазой оставлять существующий mount до
восстановления и проверки состояния всех конфигураций, которые от него зависят.
